Framework full-stack reativo e offline-first sobre Postgres padrão. Você escreve schema e funções em TypeScript; o framework cuida de reatividade, cache local-first, fila offline e conflitos — com uma engine em Rust na frente do seu banco.

Início rápido

Um comando cria um app já configurado — schema, contract, handlers, client Vite e Postgres via Docker.

# 1. crie um app Pulse já configurado
npx @onveloz/pulse new my-app
cd my-app
pnpm install

# 2. suba o Postgres (wal_level=logical) e gere os tipos
pnpm db        # docker compose up -d
pnpm gen

# 3. rode a engine e o app
pnpm engine    # engine em http://127.0.0.1:8787
pnpm dev

Pré-requisitos: Node 22+, pnpm, Docker (Postgres local). A engine em Rust é baixada automaticamente pelo @onveloz/pulse-engine; ou defina PULSE_SERVER_BIN.

Arquitetura

Uma escrita percorre nó → Postgres → reactor → SSE. A engine é dona dos pools, traduz a API de documentos para SQL e captura o conjunto de leitura/escrita de cada procedure. Quando uma escrita confirma, seu change-set é comparado com a assinatura de leitura de cada subscription — então só re-executa quem foi realmente afetado.

Schema

Tabelas e validadores em TypeScript — o validador é tipo e runtime ao mesmo tempo.

import { defineSchema, defineTable, v } from "@onveloz/pulse-schema";

export default defineSchema({
  issues: defineTable({
    title: v.string(),
    description: v.collab(),  // campo CRDT (Yjs)
    status: v.union(v.literal("todo"), v.literal("done")),
  }).index("by_status", ["status"]),
});

Funções de servidor

Implemente o contrato com implement. O ctx.db é instrumentado: cada leitura entra no conjunto de leitura.

const os = implement(contract);

export const list = os.issues.list.handler(async ({ ctx }) =>
  ctx.db.query("issues").collect(),
);

export const setStatus = os.issues.setStatus.handler(async ({ ctx, input }) => {
  await ctx.db.patch(input.id, { status: input.status });
  return null;
});

Quatro tipos: reactive (query assinável), mutation (escrita transacional), analytical (pesada, pool isolado) e action (efeitos colaterais).

Client reativo

Crie o client a partir do typeof do contrato — sem codegen. subscribe entrega o resultado inicial e cada push via SSE.

import { createClient } from "@onveloz/pulse-client";
import type { contract } from "../app/contract.js";

export const pulse = createClient<typeof contract>({
  url: "http://127.0.0.1:8787",
  headers: () => ({ authorization: "Bearer ..." }),
});

pulse.issues.list.subscribe(undefined, setIssues); // tempo real

Modo offline

Escritas via pulse.$local.mutate são otimistas e duráveis: a UI atualiza na hora, a mutation entra numa fila persistida em IndexedDB e o cache de leitura é guardado — então a app funciona até recarregando com o servidor fora do ar. Ao reconectar, a fila drena sozinha, com escrita exactly-once. 

await pulse.$local.mutate(
  ["issues", "setStatus"],
  { id, status: "done" },
  { optimistic: (store) => { /* atualiza o cache na hora */ } },
);

pulse.$onSyncStatus((s) => setLive(s === "connected"));
const pendentes = await pulse.$local.queue.size();

Você nunca resolve conflito na mão: o servidor re-executa a mutation e o client faz rebase do overlay otimista.

Colaboração (CRDT)

Campos v.collab() são documentos Yjs. Duas pessoas no mesmo campo — ou offline em duas abas — têm as edições mescladas, nunca sobrescritas. A mescla roda no servidor (Rust/yrs), dentro da transação da mutation. 

import { CollabHandle } from "@onveloz/pulse-client";

const handle = new CollabHandle(opts, {
  id, getDocPath: ["issues", "getDescription"],
  applyUpdatePath: ["issues", "applyDescription"],
}, subscribe);

CLI

pulse gen <schema.ts>                 # gera os tipos Doc/Id
pulse migrate <schema.ts> [--out f]  # DDL idempotente
pulse migrate <schema.ts> --diff     # diff do schema vs banco vivo
pulse dev <app.ts> [--port P]        # roda a engine
pulse deploy <app.ts> [--out dir]    # bundle de release
